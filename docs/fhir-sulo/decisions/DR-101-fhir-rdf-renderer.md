# DR-101 — FHIR JSON to FHIR RDF renderer

**Status:** Decided (Agent 2, FHIR ingestion)
**Date:** 2026-09-29
**Gate:** 0 / 1
**Supersedes:** nothing. **Depends on:** DR-001 (repository), plan §5 "Deployability".

## Decision

Render FHIR R4 JSON to FHIR RDF with a **purpose-built deterministic Python
renderer over the pinned profile subset**: `src/fhir_sulo/ingest/fhir_rdf.py`,
pinned as `fhir_sulo.ingest.fhir_rdf/0.1.0` in `profiles/fhir-r4-pilot.json`.

The **canonical artifact is sorted N-Triples** (`application/n-triples`), with a
human-readable nested Turtle copy beside it. No JVM, no npm, no network.

The HL7 validator CLI was evaluated and **rejected on a hard blocker**, not a
preference: it cannot emit Turtle at all.

## What was evaluated, and what was actually run

### Option A — HL7 FHIR validator CLI (`validator_cli.jar`)

Downloaded and run. It is a real option only if it can produce Turtle.

```
validator_cli.jar, latest release, 2026-09-29
  size    200,928,617 bytes
  sha256  1106b9d58f9e363e47bea7c4fc065841e5fc91fe9d062775c3bfdd212bd653cc
  self-reported version: "FHIR Validation tool Version 6.10.4 (Git# 1b90fb13f77b).
                          Built 2026-09-04T05:45:41.468Z"
```

`java` is **not installed on the host** (`/usr/bin/java` is the macOS stub:
"Unable to locate a Java Runtime"), so it was run inside
`eclipse-temurin:21-jre-alpine`. Colima shares only the VM owner's home, so bind
mounts do not work here; files were shipped in with `docker cp`.

**Blocker.** `convert` writes JSON or XML and nothing else. Asking for `.ttl`
silently produces XML:

```
$ docker exec fhirval java -jar /work/validator_cli.jar convert \
      /work/in/egfr-456.json -version 4.0.1 -tx n/a -output /work/egfr-456.ttl
 ...convert
Done. Times: Loading: 00:09.940. Max Memory = 3Gb

$ docker exec fhirval cat /work/egfr-456.ttl
<?xml version="1.0" encoding="UTF-8"?>

<Observation xmlns="http://hl7.org/fhir">
  <id value="egfr-456"/>
  ...
```

`.turtle` behaves the same way. This is not a flag we missed; it is the code.
`org.hl7.fhir.validation.ValidationEngine.convert`, line 875 of the current
`master`:

```java
public void convert(String source, String output) throws FHIRException, IOException {
  Content cnt = igLoader.loadContent(source, "validate", false, true);
  Element e = Manager.parseSingle(context, new ByteArrayInputStream(cnt.getFocus().getBytes()), cnt.getCntType());
  Manager.compose(context, e, ManagedFileAccess.outStream(output),
                  (output.endsWith(".json") ? FhirFormat.JSON : FhirFormat.XML),
                  OutputStyle.PRETTY, null);
}
```

The output format is a two-way ternary. `FhirFormat.TURTLE` exists in the
library (`org.hl7.fhir.r5.formats.RdfParser`, `org.hl7.fhir.utilities.turtle.*`
are both in the jar) but the CLI never selects it. Reaching it would require
writing and shipping a custom Java shim against `org.hl7.fhir.core` — i.e.
becoming a maintainer of a JVM component, not using a pinned tool.

Three further findings, recorded because they would have counted against
Option A even if Turtle had worked:

1. **It performs network I/O at run time, even when told not to.** With
   `-tx n/a` ("No Terminology Server") it still fetched and installed a
   package: `Installing hl7.terminology#7.4.0 to the package cache / Fetching:`.
   Our criterion was "no hidden network calls at run time".
2. **200 MB and a JVM.** Plan §5 "Deployability" says *no JVM dependency
   introduced for the mapping stack*. Ingestion is arguably outside "the
   mapping stack", so this alone would not be decisive — but it is a real cost
   against the same row's "one documented command ... with pinned versions",
   and with a hard blocker present there is no reason to pay it.
3. **Determinism unverified.** We never got to test it, because it never
   produced RDF.

### Option B — purpose-built deterministic renderer (**chosen**)

`src/fhir_sulo/ingest/fhir_rdf.py`, driven by a reviewable element table at
`profiles/fhir-r4-element-table.json`.

**It is not self-certified.** It is checked against HL7's own published R4
Turtle. HL7 publishes each R4 example as both `.json` and `.ttl`, generated by
the HL7 IG publisher. Rendering the published JSON and comparing
graph-isomorphically with the published Turtle is as close to a conformance
oracle as exists for FHIR RDF:

```
$ .venv/bin/python scripts/oracle_cmp.py     # the logic now lives in
                                             # tests/contracts/ingest/test_oracle_conformance.py
observation-example-bloodpressure: ISOMORPHIC  (168 triples, official 168)
observation-example-f205-egfr:     ISOMORPHIC  (151 triples, official 151)
encounter-example:                 ISOMORPHIC  (22 triples, official 22)
```

Those three are exactly the examples the concept note cites (§5 blood pressure,
§4 eGFR, §6 Encounter). The pairs are committed under `fixtures/r4/_oracle/` so
the check runs offline, and the test carries a control case that must *not* be
isomorphic, so it cannot pass vacuously.

Against the stated criteria:

| Criterion | Option A (validator CLI) | Option B (chosen) |
| --- | --- | --- |
| Emits Turtle/RDF at all | **No** — hard-coded JSON/XML | Yes |
| Deterministic | untested | Yes; sorted N-Triples, blank nodes labelled by a DFS in FHIR element order |
| Pinnable version | jar sha256 | module version + element-table version, both in the manifest |
| No network at run time | **No** — fetched `hl7.terminology#7.4.0` under `-tx n/a` | Yes; no module in `fhir_sulo.ingest` performs I/O beyond reading its own files |
| Round trips | untested | Yes, and the round trip is proven able to fail |
| Runs in CI unmodified | needs a 200 MB download + JVM | stdlib only |

### Option C — `fhir.resources` / other Python FHIR libraries

Not pursued. They model FHIR as Pydantic objects and none of the maintained
ones emits the R4 `fhir:` RDF form. They would add a dependency and still leave
the RDF rendering to be written.

## What is pinned

| Item | Value |
| --- | --- |
| FHIR release | 4.0.1 (R4) |
| Renderer | `fhir_sulo.ingest.fhir_rdf/0.1.0` |
| Element table | `profiles/fhir-r4-element-table.json` v0.1.0 |
| Canonical serialisation | sorted N-Triples, UTF-8, LF, no duplicate lines |
| Readable serialisation | nested Turtle, `fhir_sulo.ingest.turtle` |
| Python | 3.9 (system), standard library only at run time |
| Dev-only | `rdflib==7.1.4`, `pytest==8.3.5` (`requirements-dev.txt`) |

`rdflib` is a **development dependency only**. It is used by the oracle test to
check graph isomorphism and by nothing in `src/`. CI installs nothing, and that
test skips there; every test that could hide a fidelity loss runs on the
standard library.

## How determinism and fidelity are enforced, not hoped for

**Determinism.** Blank nodes are labelled `b0..bN` by a depth-first walk in FHIR
element order; the canonical file then sorts the lines, so even a walk-order
change cannot change the bytes. `fixtures/r4/build.py --check` re-renders every
fixture and fails on any drift, and that check runs as a unit test.

**Fidelity by refusal.** An element or type absent from the pinned element table
raises `ManifestError`. The renderer cannot silently drop anything, because it
cannot render anything it was not told about. This is why rendering HL7's
blood-pressure example first failed with
`element Observation.basedOn is not in the pinned element table` — the table
was then extended deliberately, which is the intended workflow.

**Round trip that can fail.** `rdf_to_fhir.py` rebuilds FHIR JSON from a
*parsed* graph, using a separate code path from the renderer, and
`jsonio.FhirNumber` preserves the exact lexical form of every JSON number so
`55.0` cannot come back as `55`. `tests/contracts/ingest/test_roundtrip_mutations.py`
corrupts the committed N-Triples one facet at a time and requires detection:
decimal precision, decimal value, decimal datatype, dateTime downgraded to
date, timezone change, datatype stripped, datatype inconsistent with the
lexical form, code system swap, code change, UCUM code change, unit display
text change, status change, comparator value change, comparator removal,
`Period.end` removal, reference change, `fhir:index` swap, `fhir:index`
removal, dropped component. Each case asserts the mutation actually applied,
and two control tests assert that a no-op mutation *fails* the harness.

## Deviations from HL7's published rendering, and why

Both are renderer options, default off, and both are switched on for the oracle
test so the conformance claim above is exact.

1. **`emit_code_system_class_assertions` (default off).** HL7 emits
   `a loinc:33914-3` beside a `Coding`. That is a terminology-derived OWL class
   assertion. Concept note §2: *"a code-to-class interpretation needs a reviewed
   terminology rule; a FHIR code literal alone is not an OWL class assertion."*
   Emitting it by default would put an unreviewed class assertion into the
   source layer, and would also make ingestion depend on a code-system IRI
   table that belongs to Agent 5.
2. **`emit_ontology_header` (default off).** HL7 emits
   `<...ttl> a owl:Ontology; owl:versionIRI <http://build.fhir.org/...>`. That is
   an artifact of their publisher and points at their build server. Our
   provenance is PROV-O on the derived graph (Agent 6), not an OWL header on the
   source.

A third, smaller one: a **contained** reference (`#p-inline`) gets no
`fhir:link`, because there is no external IRI to link to. The resolution is
recorded as `ReferenceEvidence(kind="contained")` instead. Inventing a link
would be inventing an identity.

## Consequences

- The mapping stack stays JVM-free and npm-free; `make contracts` runs the
  whole ingestion suite on a bare Python 3.9.
- Adding a FHIR element to scope is a reviewable diff to
  `profiles/fhir-r4-element-table.json`, not a code change.
- The pilot carries its own renderer, so a FHIR RDF spec change is our problem
  to track. Mitigation: the oracle test pins us to HL7's published output for
  three examples, and will fail if we drift from it.
- If Gate 5 needs R5, the element table is release-keyed and a second table is
  the expected shape of that change.
